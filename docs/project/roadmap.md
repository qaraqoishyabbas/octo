# Octo — roadmap стабильного первого релиза

Дата: 12 октября 2026. Baseline: `13fad8a`. Цель, выбранная пользователем: **стабильный первый релиз веб-мессенджера**.

Это новый план развития на основе [анализа](overview.md), [архитектуры](architecture.md) и [дизайна](design.md). Все задачи ниже **запланированы**, а не уже выполнены. Перечень имеющихся функций находится в overview и не дублируется как новый backlog.

## Приоритеты и статусы

- **P0:** условие допуска к пилоту с реальными аккаунтами/данными.
- **P1:** обязательная надёжность и UX первого релиза.
- **P2:** развитие после принятого первого релиза.
- Статусы: запланировано → в работе → на проверке → принято. Блокировка указывает конкретную зависимость. Код, тест и deployment evidence необходимы для статуса «принято».

Сроки не назначены: нет данных о команде, нагрузке и доступном времени. На старте этапа оценивать его отдельными проверяемыми задачами; каждому этапу назначать владельца. Рекомендуемый порядок: **R0 → R1 → R2 → R3**. Независимые задачи могут идти параллельно после фиксации соответствующего контракта.

## R0 — доступ, приватность и воспроизводимые проверки

Результат: можно безопасно принимать пилотные аккаунты и использовать достоверные проверки проекта. Начать с A1/A2, затем A3/A7 из анализа.

| ID / приоритет | Работа | Критерий готовности | Основные места |
| --- | --- | --- | --- |
| R0.1 / P0 | Ограничить админку отдельной ролью платформы | Обычный пользователь не открывает и не выполняет admin routes; владелец группы не становится platform admin; назначение роли контролируемо | routes/web, Admin/AuthController, User, migration, AdminWebTest |
| R0.2 / P0 | Закрыть private attachments и previews | Для direct/group нет обхода проверки через `/storage`; права одинаковы для preview/download/original/range; существующие файлы перенесены с проверкой сохранности | Message/Upload controllers, filesystems, media stores/composables, Nuxt cache |
| R0.3 / P0 | Определить и реализовать cache/session lifecycle | Legacy API cache удаляется; A → logout → B → offline не показывает содержимое A; pending operations и push state изолированы | nuxt.config, auth, notification, cache utils, service workers |
| R0.4 / P1 | Исправить взаимодействие notification rows | Один click/Space меняет значение один раз; DOM доступен; текущий failing test и browser check проходят | SettingNotifications.vue, notification-settings-buttons.test.ts |
| R0.5 / P1 | Настроить единый quality gate | PHP tests, web tests, admin/web builds и frontend generate воспроизводимы; проверки запускаются в CI; известные build warnings оценены | package scripts, CI config, README, composer scripts |

**Выход этапа:** отрицательные проверки прав и account isolation приложены к review, frontend suite зелёный, повторные чистые сборки подтверждены. R0.2 включает план миграции/backup файлов; смена диска без переноса не считается решением.

## R1 — надёжность сообщений, файлов и восстановления

Результат: пользователь не теряет сообщения и не создаёт дубликаты из-за сети. Зависит от R0 contracts для session/media.

| ID / приоритет | Работа | Критерий готовности | Зависимость |
| --- | --- | --- | --- |
| R1.1 / P1 | Идемпотентная отправка | Потерян ответ после commit → retry с тем же key → одно сообщение и один набор attachments; другой payload с тем же key отклоняется; конкурентные запросы проверены | R0.5; backend + frontend contract |
| R1.2 / P1 | Reconnect reconciliation | Создание/изменение/удаление/pin во время offline сходятся в открытой истории, preview и unread после reconnect; scroll anchor сохраняется | R1.1 и versioned response contract |
| R1.3 / P1 | Устойчивый file lifecycle | Ошибка move/thumbnail/DB rollback имеет определённый результат; orphan/missing files диагностируются; retry не теряет attachment | R0.2, R1.1 |
| R1.4 / P1 | Изолировать побочные эффекты отправки | Failure link sync/broadcast/push после commit не приводит к ложному провалу и дубликату; retries побочных задач безопасны | R1.1, application service design |
| R1.5 / P1 | Границы истечения/отзыва сессии | `401`, отзыв устройства и смена пользователя прекращают запросы/подписки, очищают приватный state и ведут к понятному входу | R0.3 |

**Проверка:** failure injection для потерянного ответа, database/file errors, unavailable Reverb/push; сценарии минимум с двумя browser contexts. Успешный unit mock не заменяет проверку восстановленного состояния клиента.

**Выход этапа:** текст и вложения выдерживают retry/reconnect без двойной отправки; права после исключения/отзыва обновлены; история согласована с БД.

## R2 — пользовательская приёмка веб-мессенджера

Результат: основные сценарии первого релиза работают предсказуемо на согласованных устройствах. Начинать UX-проверки можно раньше, финальная приёмка требует R1.

| ID / приоритет | Работа | Критерий готовности |
| --- | --- | --- |
| R2.1 / P1 | Mobile keyboard, scroll, overlays | При soft keyboard composer доступен; history anchor стабилен; Back закрывает нужный overlay; safe areas и orientation приняты |
| R2.2 / P1 | Единые состояния операций | Loading/empty/error/retry/offline/unknown send различимы; устаревший ответ не заменяет текущий screen; сообщение не теряется при закрытии upload UI |
| R2.3 / P1 | Доступность и локализация основных экранов | Масштабирование доступно; focus/labels/keyboard корректны; нет двойных интерактивных контролов; login/chat/settings на ru/kk/en проверены |
| R2.4 / P1 | Реальная доставка Web Push | Настроенный provider доставляет фоновые push; mute/mentions/silent/names/text/badge проверены; denied/unsupported состояния понятны; Safari принят отдельно либо ограничение явно зафиксировано |
| R2.5 / P1 | Сквозные browser regression tests | Воспроизводимые сценарии login → chat → send → receive → reply/edit/delete/pin → search → attachment; есть account switch/reconnect/revoked permission проверки |
| R2.6 / P1 | Согласовать продуктовые обещания | Интерфейс roadmap отражает новый план; папки описаны как фильтры; disabled services и экспериментальные встречи не выглядят как готовые обязательные функции |

**Выход этапа:** browser matrix и чеклист из design подписаны ответственным; все P0/P1 дефекты основного сценария закрыты. Неподдерживаемые браузеры/режимы обозначены до пилота.

## R3 — deployment, восстановление и контролируемый пилот

Результат: первый релиз подтверждён в реальном окружении и может быть восстановлен после сбоя.

| ID / приоритет | Работа | Критерий готовности |
| --- | --- | --- |
| R3.1 / P0 | Репетиция deployment | PostgreSQL migrations, HTTPS, CORS, Reverb origins, private storage, admin assets, PWA generation и queue/scheduler проверены на staging; тестового default admin password нет |
| R3.2 / P0 | Backup и восстановление | БД, вложения и необходимые ключи восстановлены в отдельном окружении; количество/связи данных и чтение файлов проверены; согласованы RPO/RTO |
| R3.3 / P1 | Наблюдаемость | Видны API errors/latency, queue failures, Reverb disconnects и storage errors; нет secrets/message bodies в logs; назначен оператор и путь реакции |
| R3.4 / P1 | Измеренный baseline нагрузки | Сценарий соответствует согласованному размеру пилота; записаны latency p50/p95, errors, message delivery lag, query count, CPU/RAM, file throughput; цели согласованы до измерения |
| R3.5 / P1 | Релизный runbook и rollback | Есть smoke checklist, порядок migrations/deploy, клиентское обновление SW, действия при failed jobs и стратегия отката с совместимостью данных |
| R3.6 / P1 | Закрытый пилот | Назначены участники/срок наблюдения; собрано feedback; нет открытых P0/P1; ограничения и поддержка понятны пользователям |

R3.1–R3.3 можно готовить до R2, но запуск пилота зависит от выхода R0/R1/R2. RPO/RTO, нагрузку и длительность пилота нельзя считать согласованными по этому документу.

**Gate первого релиза:** все обязательные задачи R0–R3 приняты, tests/builds зелёные, реальные push и two-user smoke работают, восстановление доказано, назначен ответственный за эксплуатацию. Наличие `/health` HTTP 200 не закрывает этот gate.

## После первого релиза — P2 backlog

Порядок предварительный; после пилота пересмотреть по наблюдаемым проблемам пользователей.

| Область | Следующий результат | Предпосылка |
| --- | --- | --- |
| Пересылка/share | Forward с происхождением, выбор получателей, разрешённые ссылки на сообщения | Права доступа и семантика private/public content |
| Реакции | Идемпотентные реакции, агрегаты, пользователи, realtime | Конкурентные изменения и versioned event contract |
| Голосовые | Recording, duration/waveform, playback, interruption recovery | Private media lifecycle и browser permissions |
| Поиск | Подсветка, author/date/media filters; затем глобальный поиск | Query measurements и фильтрация доступа |
| Черновики/папки | Cross-device drafts и пользовательские server folders | Conflict policy, schema/API и account isolation |
| Встречи | Закрытые room permissions, TURN, incoming calls/missed states | Отдельный design и network QA; масштаб групп — отдельное решение по media topology |
| Модерация | Reports, bans, audit, slow mode | Принятая модель ролей и журнал административных действий |
| Доступ и recovery | 2FA, восстановление и при необходимости открытая регистрация | Реальная identity/email policy и abuse handling |
| Масштабирование | Object storage, отдельные workers, Redis/search по измерениям | Baseline R3.4 и реальные bottlenecks |
| Стикеры/GIF/боты | Отдельные продукты и интеграции | Потребность пилота, лицензирование источников, scope |

Магазин, billing и массовые конференции не включены в текущий roadmap первого релиза.

## Как поддерживать roadmap

Каждая начатая задача получает owner, spec/issue, ссылки на изменения, проверки и deployment evidence. «Принято» ставится после проверки поведения, а не после появления компонента. Обнаруженный новый P0 возвращает релиз к соответствующему gate.

Документы обновляются при изменении интерфейсов, политики доступа, storage/cache и состава релиза. Экран `Roadmap.vue` отображает этапы R0–R3 и задачи после релиза из этого документа. Перенос roadmap в интерфейс выполнен; R2.6 остаётся запланированной, поскольку также включает согласование названий папок, отключённых сервисов и доступности встреч. При изменении задач синхронизировать документ и компонент.
